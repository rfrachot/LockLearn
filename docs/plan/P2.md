## P2.2 — Profiles, presets and HA-user mapping

**Status:** PASS.

**Spec:** §18, §19, §89

### Deliverables
- [x] Create profiles independent of HA users/devices.
- [x] Support personal profile onboarding and child/standard/intensive/custom presets.
- [x] Allow child/shared profiles without dedicated HA accounts.

### Exit criteria
- [x] Creating a personal profile does not make Profile == HA User.
- [x] Preset values are defaults, not irreversible restrictions.

Implementation note: Home Assistant ConfigFlow context does not identify the authenticated
HA user. The config-flow checkbox remains a setup preference; idempotent personal-profile
creation is exposed by the profile service and is intended to be invoked from the first
authenticated LockLearn bootstrap surface in P2.6. This preserves `Profile != HA User`
without guessing an owner during config-entry setup.

## P2.3 — Backend ACL and privacy filtering

**Status:** PASS.

**Spec:** §20, §21, §22, §23, §60, §94, §109, §116, §117

### Deliverables
- [x] Implement owner/editor/viewer permission matrix in one backend authority.
- [x] Filter unauthorized private profiles out of listings entirely.
- [x] Keep HA admin distinct from automatic profile ownership.
- [x] Add negative authorization tests for the ACL service boundary; endpoint-specific negative tests remain owned by P2.6 when profile CRUD endpoints exist.

### Exit criteria

- [x] Frontend permission checks are convenience only.
- [x] HA entity/event privacy caveats are documented.

## P2.4 — Track configuration, pack pinning and card rules

**Status:** PASS.

**Spec:** §24, §25, §26, §27, §76

### Deliverables

- [x] Pin pack_version and expose explicit integrate-update service action.

## P2.5 — Learning quotas, goals and load forecast

**Status:** PASS.

**Spec:** §25, §27, §29, §35, §58

### Deliverables
- [x] Implement card-based new/review quotas and profile-preset new-card defaults.
- [x] Add target_date/coverage/retention goal model.
- [x] Estimate review load at ~3 weeks/~3 months and notification-vs-active-session share.

### Exit criteria
- [x] Quotas count CardDefinitions, never LearningItems.
- [x] UI can warn when configured demand is structurally infeasible.

Implementation note: the spec defines numeric preset defaults only for new-card
quotas (3/8/15), not review ceilings. P2.5 therefore requires an explicit
`max_reviews_per_day_cards` instead of inventing preset values.
