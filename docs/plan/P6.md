## P6.7 — Performance, scale and storage-budget validation

**Spec:** §68, §69, §74.5.1, §80

**Status:** PASS — implemented and qualified on `feat/p6-hardening`.

### Deliverables
- [x] Benchmark answer/next-card/scheduler/content activation against P0-accepted budgets.
- [x] Estimate/test 5-year state.db growth and dataset disk/free-space thresholds.
- [x] Instrument structured internal metrics/logs without auto-exposing them as HA sensors.

### Exit criteria
- [x] Performance numbers are measured on documented reference hardware.

**Implementation (2026-09-27):** P6.7 reuses the permanent P5.9 wall-clock gate
for session answer, next-card selection and scheduler generation rather than
duplicating those algorithms. `scripts/p6_7_scale_validation.py` adds a
60,000-card normalized content build/activation qualification plus a 1,826-day
`state.db` materialization using the real state schema. The state scenario uses
the current Standard new-card default (8/day), the documented P3.14 Standard
quality-bench capacity (80 verified reviews/day), four 20-card sessions/day,
six notification slots/day and two small audit events/day. It reports the real
SQLite file size, page geometry, row counts and MiB/year without inventing a
state-size PASS threshold absent from the spec.

Dataset budgets are centralized at 150 MiB per official artifact and a 500 MiB
aggregate reconstructible-cache warning. Activation requires at least twice the
estimated generated package-set footprint plus a 32 MiB safety margin; new
manifests sign at least the equivalent per-dataset floor, while runtime
recomputes the maximum for historical signed packages. The 500 MiB condition is
WARNING-only, auto-clears below threshold and never invalidates already usable
content.

Process-local bounded metrics now cover writer-queue wait, session answer,
scheduler slot generation and detected clock drift, content build and content
activation. Metrics expose only count/last/p95/max timing aggregates in redacted
diagnostics and DEBUG logs; they are not persisted and do not become HA
entities/sensors. Existing Repair/diagnostic paths remain the source for
unresolved targets and notification/scheduler failure status.

No state/content schema migration and no frontend production-source change are
part of P6.7.

**Qualification (2026-09-27, HEAD
`f05aab04b48baf8f8f73937cb8b3c5039e4d5b3d`):** PASS on the documented
reference VM (CPython 3.14.4, Linux 7.0, 6 logical CPUs, 15 GiB RAM). P5.9
measured session-answer p95 1.137 ms (<100 ms), next-card p95 62.046 ms
(<150 ms) and scheduler-day p95 4.064 ms (<250 ms). The integrated P6.7 rerun
measured 1.150 ms, 65.403 ms and 3.983 ms respectively.

The 60,000-card qualification produced a 137,302,016-byte source package and a
177,299,456-byte candidate/active generation; build took 4.724 s and activation
1.640 s. Required activation free space was 388,153,344 bytes and the runtime
gate passed. The 1,826-day state projection produced a 218,955,776-byte
`state.db` (41.74 MiB/year), `PRAGMA integrity_check=ok` and zero foreign-key
violations.

Ruff format/lint, mypy (166 sources), resource validation, targeted pytest
(57 passed), full pytest (464 passed, one known duplicate-ZIP-name warning),
frontend typecheck/tests/build (49 tests) and `git diff --check` all passed.
The generated frontend bundle remained byte-identical at
`d1626186b8fe1cf50f81efb5a4f3dd05de3dd54e22ec86b20612000c9b259385`.
